# 民泊清掃スケジュール・チェックリストアプリ 要件定義書

- ドキュメント種別: 要件定義書
- プロジェクト名: cleaning_schedule
- 作成日: 2026-09-07 / 更新日: 2026-09-07（v1.1）
- ステータス: 承認済み（2026-09-07）。実項目・テンプレ・ユーザーは運用開始後に登録

---

## 1. 背景・目的

民泊（Airbnb）1物件の運営において、ゲストのチェックアウト後に行う清掃作業を
チーム4名で分担している。現状は清掃の実施漏れ・品質のばらつき・実施記録の欠如が課題。

本アプリは以下を実現する。

- Airbnb の予約カレンダー（iCal）から清掃が必要な日を自動で洗い出す
- 清掃当日に、部屋ごとのチェックリストをスマホで確認しながら作業できる
- 清掃完了のエビデンス（写真・実施者・実施時刻）を記録・保管する
- 4名の誰が・いつ・何を実施したかを後から確認できる

清掃の割り当て（当番決め）は本アプリのスコープ外。4名は状況に応じて各自が担当する。

---

## 2. 対象ユーザー

| 役割 | 人数 | 権限 |
|---|---|---|
| 民泊管理者 | 1 | 一般（清掃実施・記録） |
| 民泊管理者のパートナー | 1 | 一般（清掃実施・記録） |
| ツール管理者（本人） | 1 | 管理（設定・ユーザー管理・同期）＋一般 |
| ツール管理者の配偶者 | 1 | 一般（清掃実施・記録） |

- 全員が清掃作業を担当する。
- 一般権限と管理権限の差は「設定変更・iCal URL変更・ユーザー追加削除」のみ。
  日常の清掃記録操作は全員同じ。

---

## 3. 利用シーン・前提

- 利用端末: スマートフォン（iOS / Android）中心。PC は補助。
- 利用形態: ブラウザで開き「ホーム画面に追加」してアプリのように起動（PWA）。
- 利用場所: 主に物件内での清掃作業中。通信環境は物件の Wi-Fi または携帯回線。
- チェックアウト時刻は 10:00 固定。清掃はその日の午後に実施。
- 複数物件に対応する。物件ごとに iCal URL・チェックリスト・清掃タスクを個別管理する。
- タイムゾーンは Asia/Tokyo 固定。

## 4. スコープ

### 4.1 本リリースに含む（In Scope）

1. 複数物件の管理（物件の追加 / 編集、物件ごとの iCal URL 設定）
2. Airbnb iCal の定期取得と予約データの同期（物件ごと）
3. 予約（チェックアウト）から「清掃タスク」を自動生成
4. 清掃タスクの一覧表示（全物件横断 / 物件別、今後の予定・直近の実施済み）
5. 清掃タスク詳細でのチェックリスト操作（部屋・エリア別項目のチェック）
6. チェックリストテンプレートの管理（ベーステンプレート、物件別・部屋別のカスタマイズ、項目の編集）
7. 写真エビデンスのアップロードと表示
8. 清掃の「開始」「完了」ステータス管理と実施者・時刻の記録
9. 過去の清掃履歴とエビデンスの閲覧
10. 4名のログイン（個人識別）
11. PWA 対応（ホーム画面追加、アプリシェルのオフラインキャッシュ）

### 4.2 本リリースに含まない（Out of Scope）

- 当番・シフトの自動割り当て
- 清掃業者への外部通知（メール / LINE / Slack）※将来検討
- 物件ごとの権限分離（誰がどの物件を見られるか）※全ユーザーが全物件を扱える前提
- 在庫・備品管理、請求・報酬計算
- ゲストとのやり取り、予約管理そのもの
- 完全なオフライン作業（写真のオフラインキュー等）※将来検討

## 5. 機能要件

### 5.0 物件管理

- FR-0a: 管理権限ユーザーは物件を追加・編集・無効化できる。
  属性: 物件名、iCal URL（Secret 扱い）、既定チェックアウト時刻（既定 10:00）、メモ。
- FR-0b: 物件ごとに使用するチェックリストテンプレートを割り当てる。
- FR-0c: 無効化した物件は同期・タスク生成の対象外とする（既存の履歴は保持）。

### 5.1 iCal 同期

- FR-1: 各物件の iCal URL を定期取得する（既定: 3時間ごと、Cron）。物件ごとに実行。
- FR-2: 画面から「今すぐ同期」を実行できる（全物件 / 物件指定）。
- FR-3: iCal のイベントを解析し、Airbnb の「予約」と「ブロック（Not available）」を判別する。
  予約のみを清掃対象とする。
- FR-4: 予約イベントから以下を取得: 予約UID、チェックイン日、チェックアウト日、
  ゲスト識別のヒント（電話番号下4桁等、取得可能な範囲）、元テキスト。
- FR-5: 同一 UID の予約が更新・キャンセルされた場合、同期時に反映する
  （日程変更 → 清掃日更新、キャンセル → 清掃タスクを取消状態に）。
- FR-6: 同期の最終実行時刻と結果（成功 / 失敗・件数）を物件ごとに記録・表示する。

### 5.2 清掃タスク生成

- FR-7: 予約のチェックアウト日ごとに、その物件の清掃タスクを1件生成する。
- FR-8: 清掃日 = チェックアウト日。表示上「午後実施」を明示する。
- FR-9: 予約に紐づかない臨時清掃を手動で追加できる（物件を指定）。
- FR-10: 清掃タスク生成時に、その物件に割り当てられたチェックリストテンプレートを
  展開して項目をスナップショットとして作成する（以後テンプレートを変更しても既存タスクは不変）。

### 5.2.1 チェックリストテンプレート管理

- FR-10a: 「掃除場所（エリア／部屋）」単位で項目をまとめたテンプレートを用意する。
- FR-10b: 共通のベーステンプレートを1つ以上持ち、新規物件作成時の初期値として複製できる。
- FR-10c: 物件ごとにテンプレートを保持し、エリア・項目を追加／編集／削除／並べ替えできる。
- FR-10d: 各項目に「写真必須」フラグと補足メモを設定できる。
- FR-10e: テンプレート編集は管理権限のみ。編集は既存の清掃タスクには遡及しない（FR-10）。
- FR-10f: 部屋単位のカスタマイズは、テンプレート内でエリア（=部屋）を自由に定義することで実現する。

### 5.3 清掃タスク一覧（トップ画面）

- FR-11: 「今後の清掃」（未完了・未来日含む）と「最近完了した清掃」を分けて表示。
- FR-12: 各カードに表示: 物件名、清掃日、曜日、状態（未着手 / 作業中 / 完了）、
  担当者（開始 or 完了した人）、チェックリスト進捗（例 8/15）。
- FR-13: カードをタップで詳細へ遷移。
- FR-14: 既定表示は全物件横断の直近1〜2週間。物件で絞り込みできる。過去は「履歴」画面で遡れる。

### 5.4 清掃タスク詳細・チェックリスト

- FR-15: 部屋・エリアごとにグルーピングしてチェックリストを表示。
- FR-16: 各項目をタップでチェック / チェック解除。チェック者と時刻を記録。
- FR-17: 「写真必須」の項目は、写真が1枚以上ないと完了にできない。
- FR-18: 清掃全体に対して「開始」ボタン（状態→作業中、開始者・時刻を記録）。
- FR-19: 「完了」ボタン（全必須項目クリアで押下可、状態→完了、完了者・時刻を記録）。
- FR-20: フリーテキストのメモ欄（引き継ぎ・気づき）。
- FR-21: 完了後も再編集できる（誤操作対応。編集履歴は最小限で可）。

### 5.5 写真エビデンス

- FR-22: 清掃タスク単位、または特定チェック項目に紐づけて写真を追加できる。
- FR-23: 撮影 / ライブラリ選択の両方に対応（スマホの標準ファイル選択）。
- FR-24: アップロード前にブラウザ側で長辺約1600pxへ縮小・再エンコード（JPEG）。
- FR-25: 保存時にアップロード者・サーバー受信時刻・任意キャプションを記録。
- FR-26: 一覧・詳細でサムネイル表示、タップで拡大表示。
- FR-27: アップロード者本人および管理権限は写真を削除できる。

### 5.6 履歴・閲覧

- FR-28: 過去の清掃タスクを日付降順で一覧。
- FR-29: 清掃ごとの実施者・所要時間（開始〜完了）・写真・メモを参照できる。
- FR-30: （任意）期間指定で実施記録を CSV / JSON エクスポート。

### 5.7 認証・ユーザー

- FR-31: 4名の登録ユーザーから名前を選び、個人PIN（4〜6桁）でログイン。
- FR-32: ログイン状態は署名付き Cookie で約90日保持（頻繁な再ログインを避ける）。
- FR-33: ログアウト操作を提供する。
- FR-34: 管理権限ユーザーは、物件（iCal URL 含む）・チェックリストテンプレート・
  ユーザーの追加/削除/PINリセットを行える。
- FR-35: 未ログイン時は全ページをログイン画面へリダイレクト（PWA manifest 等の静的資産を除く）。
- FR-35a: 初期ユーザーは事前投入せず、各自がセルフ登録する。
  登録は共有シークレット（SETUP_TOKEN）付きの登録URLから行い、表示名とPINを本人が設定する。
  最初の登録者を admin とし、以降は member（admin が後から権限変更可）。
  登録は上限人数到達で自動停止、admin が再開/停止できる。

### 5.8 PWA

- FR-36: Web アプリマニフェストを提供し「ホーム画面に追加」に対応。
- FR-37: アイコン（各サイズ）、テーマカラー、スタンドアロン表示。
- FR-38: Service Worker でアプリシェル（HTML/CSS/JS/アイコン）をキャッシュし、
  再訪問時の起動を高速化。データAPIはネットワーク優先。

## 6. 非機能要件

- NFR-1 パフォーマンス: 主要画面の初回表示 2 秒以内（携帯回線想定）。写真は遅延読み込み。
- NFR-2 可用性: Cloudflare Workers / D1 / R2 の標準SLAに準拠。障害時は同期スキップし次回リトライ。
- NFR-3 セキュリティ:
  - PIN はハッシュ化して保存（平文保存しない）。
  - Cookie は HMAC 署名・HttpOnly・Secure・SameSite=Lax。
  - iCal URL とトークンは Secret / DB で管理し、画面・ログに出さない（URLは編集時のみマスク表示）。
  - 写真・記録は認証済みユーザーのみアクセス可。R2 への直接公開URLは使わない（Worer 経由で配信）。
- NFR-4 プライバシー: ゲスト個人情報は最小限（識別ヒント程度）のみ保持。予約の生テキストは
  同期用途に限定し画面表示しない。
- NFR-5 コスト: Cloudflare 無料枠〜低額枠に収める（D1・R2・Workers のリクエスト/容量）。
  - 写真は縮小保存（FR-24）。1枚あたり目安 200〜400KB。R2 無料枠は 10GB/月。
  - 容量が増えた場合の運用（古い写真のアーカイブ / 解像度見直し）は NFR-7 とあわせ運用手順書で定める。
- NFR-6 保守性: ビルド工程は最小限。設定は wrangler.jsonc に集約。
- NFR-7 データ保持: 清掃記録・写真は最低2年間保持。自動削除はしない（手動運用）。
  写真総量は定期的に確認し、閾値超過時に運用判断する（07_運用手順.md で定義）。
- NFR-8 対応ブラウザ: iOS Safari / Android Chrome の最新2バージョン。
- NFR-9 スケール前提: 物件数 〜10、月間清掃 〜100 件程度を想定。これを大幅に超える場合は再設計。

## 7. データ設計（論理・概要）

複数物件を前提とし、すべての清掃・予約・テンプレートは `property` に紐づく。

- property: id, name, ical_url, active(bool), checkout_time(既定 "10:00"),
  template_id(使用テンプレート), note, created_at
- reservation: id, property_id, ical_uid, checkin_date, checkout_date, guest_hint,
  status(active/cancelled), raw_text, synced_at
- cleaning: id, property_id, reservation_id(NULL可), clean_date,
  status(pending/in_progress/done/cancelled), started_by, started_at,
  completed_by, completed_at, note, created_at
- checklist_item: id, cleaning_id, area_label(部屋/エリア), sort_order, key, label,
  needs_photo(bool), note, checked(bool), checked_by, checked_at
  （テンプレートから生成時にスナップショット。以後テンプレ変更の影響を受けない）
- photo: id, property_id, cleaning_id, checklist_item_id(NULL可), r2_key, content_type,
  size_bytes, uploaded_by, uploaded_at, caption
- user: id, name, role(admin/member), pin_hash, active(bool), created_at
- checklist_template: id, name, is_base(bool), property_id(NULL=ベース), created_at, updated_at
- checklist_template_item: id, template_id, area_label, sort_order, key, label,
  needs_photo(bool), note
- sync_log: id, property_id, run_at, result(ok/error), reservations_seen,
  cleanings_created, message

補足:

- 新規物件作成時、ベーステンプレート（is_base=true）を複製して物件専用テンプレートを作る。
- テンプレートの area_label が「部屋」に相当する。部屋単位のカスタマイズは項目の増減で表現する。

## 8. 外部インターフェース

### 8.1 Airbnb iCal

- 取得方式: HTTPS GET（URLにトークン付き）。認証不要。
- URL は Secret として保管（本書には記載しない）。
- 形式: iCalendar（VEVENT の集合）。
  - 予約: SUMMARY が "Reserved" 等、DESCRIPTION に予約詳細/URL を含む。
  - ブロック: SUMMARY が "Airbnb (Not available)"。清掃対象外。
  - 日付: DTSTART=チェックイン日、DTEND=チェックアウト日（VALUE=DATE、終了日は排他）。
- 取得失敗・パース不能イベントはスキップし sync_log に記録。

### 8.2 ストレージ

- Cloudflare D1: 上記データ（写真バイナリを除く）。
- Cloudflare R2: 写真バイナリ。キーは `property/{id}/cleaning/{id}/{uuid}.jpg` 形式。
- 注意: 対象アカウントでは R2 が未有効化。ダッシュボードで R2 を有効化する必要がある
  （無料枠あり。有効化には支払い方法の登録が必要な場合がある）。有効化できない場合の代替は §9 Q5 参照。

## 付録A. Hono とは（Q1 の補足）

**Hono（炎）** は Cloudflare Workers 向けに広く使われている軽量な Web フレームワーク。
Express に似た書き味で、ルーティング・リクエスト/レスポンス・Cookie・ミドルウェア・
静的配信・JSX での HTML 生成などを提供する。

- 依存は Hono 1つのみ。ビルド工程は不要（`npm i hono` だけ）。動作は数十KB規模で軽量。
- 素の Worker（`fetch(request)` 内で `if (url.pathname === ...)` を分岐）だと、
  ルーティング・認証チェック・Cookie 署名・フォーム解析・エラー処理を全て自前で書くことになる。
  本アプリは画面・APIが20以上になる見込みで、素の実装は保守が重くなる。
- Hono を使うと例えば以下のように書ける:

  ```js
  app.get('/cleaning/:id', auth, async (c) => {
    const job = await getCleaning(c.env.DB, c.req.param('id'))
    return c.html(renderCleaning(job))
  })
  app.post('/cleaning/:id/photo', auth, async (c) => { /* R2 保存 */ })
  ```

- デメリット: 依存が1つ増える／わずかな学習コスト。いずれも小さく、採用を推奨。

判断: **Hono を採用**。基本設計書（02）で具体的な構成を確定する。
